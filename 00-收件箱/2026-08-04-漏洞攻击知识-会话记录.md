# 漏洞攻击知识学习记录

日期：2026-08-04
主题：漏洞利用与漏洞攻击共性

## 一句话结论

漏洞攻击的本质是：攻击者通过 URL 参数、HTTP 头、Cookie、请求体、上传文件、API 参数等外部可控输入点构造异常内容，诱导系统内部的解析器、执行器、认证模块或文件系统把“数据”误当成“指令、路径、身份、脚本、查询或配置”处理，从而造成越权读取、写入、执行、绕过或控制。

## 漏洞利用是什么

漏洞利用是指攻击者把系统、应用、框架、组件、协议或配置中的缺陷转化为实际攻击效果的过程。

也就是说，系统原本只应该接收普通数据，但因为输入校验、权限控制、解析逻辑、配置安全、业务逻辑或组件实现存在问题，攻击者可以让系统产生非预期行为。

常见结果包括：

- 读取不该读取的数据
- 写入或修改不该修改的数据
- 执行系统命令或程序代码
- 绕过登录、认证或权限控制
- 访问内部服务或敏感文件
- 触发服务器外联
- 获取系统、组件、路径、账号、配置等敏感信息

## 漏洞攻击的共同点

这些漏洞攻击虽然名称很多，例如 SQL 注入、远程命令执行、XSS、任意文件读取、文件上传、模板注入、XXE、反序列化、未授权访问、Shiro、Log4j、Weblogic、ThinkPHP 等，但底层有共同规律。

共同点可以总结为：

- 都存在一个外部可控入口
- 都依赖系统处理不可信输入
- 都试图影响某个解析器、执行器或权限判断逻辑
- 都发生在信任边界附近
- 都希望造成读取、写入、执行、绕过、探测或外联等结果
- 很多攻击可以串联成攻击链
- 单条告警通常只能证明“发生了尝试”，是否成功需要结合响应和日志判断

## 常见攻击入口

攻击者经常把构造内容放在这些位置：

- URL 参数，例如 `?id=1`
- URL 路径，例如 `/download/file/xxx`
- HTTP 请求头，例如 `User-Agent`、`Referer`、`X-Forwarded-For`
- Cookie
- POST 表单参数
- JSON 请求体
- XML 请求体
- 文件上传字段
- API 参数
- WebSocket 消息
- 搜索框、评论框、登录框等业务输入点
- 后台管理接口
- 暴露在公网的服务端口

## 常见被影响的组件

漏洞攻击通常不是“凭空生效”，而是影响某个具体组件：

- 数据库：SQL 注入
- 浏览器：XSS
- 操作系统 Shell：命令执行
- 编程语言解释器：代码执行
- 模板引擎：模板注入
- XML 解析器：XXE
- 文件系统：文件读取、文件包含、文件上传
- 序列化框架：反序列化漏洞
- 认证模块：未授权访问、认证绕过
- 日志组件：Log4j 类漏洞
- Web 框架：Struts2、ThinkPHP、Laravel、Spring 等漏洞
- 中间件和服务：Weblogic、Tomcat、Jboss、ActiveMQ、Solr、ElasticSearch 等漏洞
- 网络设备和 VPN：路由器、SSL-VPN、堡垒机等漏洞

## 攻击行为分类

| 攻击类型 | 具体行为 | 系统错误点 | 可能影响 |
|---|---|---|---|
| SQL 注入 | 在参数中构造数据库语义 | 用户输入被拼接进 SQL 查询 | 数据泄露、数据篡改、绕过登录 |
| XSS | 在输入点插入脚本内容 | 用户输入被当成 HTML/JS 输出 | 盗取会话、钓鱼、页面篡改 |
| 命令执行 / RCE | 在参数、请求头或请求体中构造命令或代码 | 外部输入进入命令行、解释器或危险函数 | 服务器被控制、执行系统命令 |
| 文件读取 | 修改路径参数读取敏感文件 | 文件访问范围限制不足 | 泄露配置、密钥、源码 |
| 文件上传 | 上传可执行文件或伪装文件 | 文件类型、路径、执行权限控制不足 | WebShell、代码执行 |
| 文件包含 | 控制被包含的文件路径 | 用户输入被当作本地或远程文件路径 | 读取文件、代码执行 |
| XXE | 在 XML 中构造外部实体 | XML 解析器允许外部实体 | 读取文件、访问内网、外联验证 |
| 模板注入 | 在模板参数中插入表达式 | 模板引擎执行了用户输入 | 信息泄露、代码执行 |
| 反序列化 | 提交恶意序列化对象 | 程序信任了不可信对象数据 | 代码执行、权限绕过 |
| 未授权访问 | 直接访问后台、接口或资源 | 缺少认证或权限校验 | 数据泄露、非法操作 |
| 认证绕过 | 构造特殊请求绕过登录判断 | 鉴权逻辑存在缺陷 | 冒充用户、进入后台 |
| 信息泄露 | 访问调试接口、错误页面、配置文件 | 敏感信息暴露 | 辅助后续攻击 |
| SSRF / 外联 | 让服务器访问攻击者指定地址 | 服务端请求目标未限制 | 探测内网、访问云元数据、DNSLog 回连 |
| CRLF / 头注入 | 在参数中插入换行控制字符 | 用户输入污染响应头或日志 | 响应拆分、头注入、日志伪造 |

## 安全运营看告警包的方法

看一条漏洞攻击告警包时，可以按下面顺序分析。

### 1. 看请求方法和路径

关注：

- 是 `GET`、`POST` 还是其他方法
- 访问的是哪个路径
- 是普通业务页面、API、后台接口，还是静态资源
- 路径是否包含可疑内容，例如目录穿越、特殊后缀、框架漏洞路径

示例：

```http
POST /Comments.aspx?id=ACUSTART%0D%0AACUEND HTTP/1.1
```

这里的入口是 `/Comments.aspx` 页面上的 `id` 参数。

### 2. 看可控输入点

重点看攻击内容出现在哪里：

- URL 参数
- HTTP 头
- Cookie
- 请求体参数
- JSON 字段
- XML 字段
- 上传文件名或文件内容

### 3. 看特殊字符和编码

常见可疑内容包括：

- SQL 相关字符：`'`、`"`、`or`、`union`、`select`
- 命令执行相关字符：`;`、`|`、`&&`、反引号、`$()`
- 路径穿越：`../`、`..\`
- XSS：`<script>`、`onerror=`、`javascript:`
- 模板表达式：`${}`、`{{}}`、`<% %>`
- XML 外部实体：`<!ENTITY`
- CRLF：`%0D%0A`
- 反序列化特征：Java、PHP、Fastjson、Shiro、Ysoserial 等相关结构或特征
- DNSLog / 外联域名

### 4. 看工具特征

有些请求明显来自扫描器或漏洞利用工具。

常见特征：

- `sqlmap`
- `WVS` / `Acunetix`
- `Netsparker`
- `AppScan`
- `Wfuzz`
- `Joomscan`
- `WebReaver`
- `Webshag`
- 特定扫描器的 User-Agent、请求头、测试标记、随机参数

注意：工具特征只能说明“像扫描器”，不能单独证明攻击成功。

### 5. 看攻击意图

尝试判断这条请求想影响哪个组件：

- 数据库：可能是 SQL 注入
- 浏览器：可能是 XSS
- Shell 或解释器：可能是命令执行 / 代码执行
- 文件系统：可能是文件读取、上传、包含
- XML 解析器：可能是 XXE
- 模板引擎：可能是模板注入
- 认证模块：可能是未授权访问或认证绕过
- 服务端请求功能：可能是 SSRF 或 DNSLog 外联验证

### 6. 看响应判断是否成功

单看请求包通常只能判断“有攻击尝试”。是否成功需要看响应包和日志。

成功或高风险迹象包括：

- 响应中回显攻击标记
- 返回敏感文件内容
- 返回数据库报错、堆栈信息或系统路径
- 状态码异常，例如 500、302 到异常地址、200 且返回敏感内容
- 出现 DNSLog、HTTP 回连、LDAP/RMI 回连等外联记录
- 服务器产生异常进程
- Web 目录出现新文件
- 日志中出现执行命令、写文件、访问内网地址等行为
- 认证前接口返回了认证后数据

不确定项必须标注：

- 只有请求包，没有响应包：只能判断为攻击尝试，不能确认成功
- 只有 WAF 告警，没有后端日志：不能确认业务系统实际处理了请求
- 只有扫描器特征：不能确认漏洞存在
- 只有 200 状态码：不能单独确认攻击成功，需要看响应内容

## 示例：CRLF 注入探测告警

请求示例：

```http
POST /Comments.aspx?id=ACUSTART%0D%0AACUEND HTTP/1.1
user-agent: WVS/12.0
acunetix-aspect: enabled
host: testaspnet.vulnweb.com
content-type: application/x-www-form-urlencoded
```

分析：

- `WVS/12.0` 和 `acunetix-*` 请求头表明该请求具有 Acunetix 扫描器特征
- `id=ACUSTART%0D%0AACUEND` 中 `%0D%0A` 是 CRLF，也就是回车换行
- `ACUSTART` 和 `ACUEND` 是扫描器用于验证回显或注入位置的标记
- 该请求大概率是在测试 CRLF 注入、HTTP 头注入或响应拆分类问题

不确定内容：

- 仅凭该请求包不能确认漏洞利用成功
- 需要查看响应头、响应体、WAF 动作、Web 日志和服务端日志
- 如果响应头或响应体中出现 `ACUSTART` / `ACUEND`，风险会升高
- 如果 WAF 已拦截且后端无访问日志，则更可能是被拦截的扫描尝试

可写研判结论：

> 发现具备 Acunetix WVS 特征的扫描请求，对 ASP.NET 页面 `/Comments.aspx` 的 `id` 参数插入 `%0D%0A` 换行控制字符，并使用 `ACUSTART/ACUEND` 标记测试是否存在 CRLF 注入、HTTP 头注入或响应拆分风险。当前仅凭请求包只能判断存在漏洞扫描或探测行为，是否成功需结合响应内容、响应头、WAF 动作、Web 日志和主机日志进一步确认。

## 通用研判模板

```text
攻击入口：URL 参数 / HTTP 头 / Cookie / 请求体 / 文件上传 / API
可控输入：攻击者构造的特殊字符、编码、路径、语句、对象、脚本或外联地址
触发组件：数据库 / 浏览器 / Shell / 模板引擎 / XML 解析器 / 文件系统 / 认证模块 / 反序列化组件
攻击意图：读数据 / 写文件 / 执行代码 / 绕过权限 / 探测信息 / 建立外联
当前证据：请求包 / 响应包 / WAF 告警 / Web 日志 / 主机日志 / 外联日志
是否成功：明确成功 / 明确拦截 / 仅攻击尝试 / 证据不足
不确定项：缺少响应包、缺少后端日志、缺少外联记录等
```

## 一句话研判句式

> 该告警表现为攻击者通过外部可控输入点构造异常参数，尝试影响后端解析或执行逻辑，使系统在数据库查询、脚本渲染、命令执行、文件访问、对象解析或权限校验过程中产生非预期行为。当前需结合响应内容、状态码、外联记录、WAF 动作和主机日志判断是否利用成功。

## 学习重点

- 不要只记漏洞名称，要看攻击输入进入了哪里
- 不要只看请求包，要尽量看响应包和服务端日志
- 不要把“扫描尝试”直接等同于“攻击成功”
- 看到编码字符要先解码再分析
- 看到扫描器特征要记录工具来源，但仍需判断影响
- 判断成功与否要依靠证据，不确定就明确写“不确定”
