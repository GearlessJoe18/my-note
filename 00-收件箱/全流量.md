### A. 启动与进程编排（业务）

| 项    | 内容                                                                                 |
| ---- | ---------------------------------------------------------------------------------- |
| 关键文件 | `realeye/source/main.c`                                                            |
| 职责   | 读 `-c` 配置、清临时目录、加载规则、启动 DPDK 框架、拉统计线程、定时热更规则                                       |
| 输入   | 命令行 `-c restore.ini`；规则文件 `/zrtx/para/realeye/rules/rule_encode_key.php`           |
| 输出   | 调用 `main_dpdk(...)` 把 4 个回调交给框架；另写流量统计到 `/u2/workdir/1001/flow/`、`/var/detectlog/` |

`flow_init()` 在 `main` 里被注释掉了，启动时不会跑。

### B. 业务回调：把框架解析结果写成日志（核心业务）

|项|内容|
|---|---|
|关键文件|`realeye/source/restore.c`、`restore.h`|
|职责|框架解析完一条流/告警后回调这里；拼 JSON，写磁盘|
|输入|框架传入的 `node_stat`（五元组、包数字节数）、`flowid`、`DATA_INFO`（HTTP/告警/协议字段）|
|输出|访问日志、告警日志（路径来自框架配置 `g_port_cfg__access_log_file_path` / `g_port_cfg__alert_log_file_path`）；黑名单日志写 `/dev/shm/blackdb`|

四个注册函数（在 `main()` 里交给 `main_dpdk`）：

1. `restore_access_log_callback`：会话/访问日志 JSON
2. `restore_monitor_log_callback`：告警 JSON（命中 Snort 规则时带 payload、规则 ID）
3. `user_define_writepcap_callback`：当前直接 `return`，全流量 PCAP 落盘后本目录不再搬文件
4. `file_data_second_process`：文件还原二次处理，协议分支被 `#if 0` 关掉，等于原样交回框架

## 启动入口

进程入口 main.js
真正处理「业务数据」的入口是框架回调

---


main（）流程
1、配置文件拷进全局变量restore_ini_path 供后面函数调用

2、内核申请：把本进程的 nice 设成 0。
- 成功：真正的结果是内核里这个进程的调度优先级变成 0，之后所有线程（含 `main_dpdk`、`PacketThread`）都跑在这个优先级上。
- 失败：`perror` 往 标准错误（终端/日志） 打一行 `setpriority: ...`，然后照常往下走。后面初始化照旧，只是优先级可能仍是启动时继承来的值。
  
3、固定读 `rule_encode_key.php` 全文 → 用 `str_authcode` 
（密钥在函数内部自己找，顺序是：

1. 若存在 `/zrtx/ini/old_key.flg` → 用代码里写死的 `UC_KEY`
2. 否则去 `/zrtx/center_data/web/conf/sys_conf.xml` 里读 `<Decry_rule_key>...</Decry_rule_key>`
3. 还读不到 → 仍用那个写死的 `UC_KEY`）
按上面那套密钥解密 → 明文由 `pRule` 指向 → 写到 `/root/1.json`。读文件失败则整步跳过。

4、在收包、还原开始之前，把上次运行留在临时目录里的旧文件清掉，避免新进程把残留文件当成当前任务。

5、① `GlobalInit`：记下有哪些网口（给统计用）

- 输入： 第 1 步拿到的 ini 路径（`-c`），例如 `restore.ini`
- 处理： 读 `[DPDK] dpdk.port_num`，再按 `[PORT0]`、`[PORT1]`… 读每个口的 `port.pci_addr`，计数器清零
- 输出： 填进本文件全局数组 `m_DpdkInfo[]`，个数放在 `m_nDpdkCount`
- 给谁： 后面的 `PacketThread`。它按 PCI 去读网卡统计、写流量文件。  
     不把 DPDK 拉起来；真正绑核、开网口是后面的 `main_init` / `main_dpdk` 再读同一份 ini。

---

② `combine_rule_queue_init`：装组合规则表（给告警字段用）

- 输入： 固定文件 `/zrtx/center_data/data/rule_files/local_mrule.php`（加密 JSON）。不是 第 3 步那个 `rule_encode_key.php`，也不读 `/root/1.json`
- 处理： 同样 `str_authcode` 解密 → 解析每条规则的 `cm_id`、`qr_ids`/`fr_ids`、`ca_name`、`cm_level` → 放进哈希表
- 输出： 全局表 `g_table_qr_fr`
- 给谁： 后面 `restore.c` 写告警日志时，用 `combine_rule_check_sid_qr_fr_rule` 按 sid 查出规则名、严重级别。表没装好，告警里这些字段就是空的。

---

③ `map_protocol_load`：装协议名映射（给还原日志用）

- 输入： 固定目录 `/zrtx/para/realeye/protocol` 下的 JSON 文件
- 处理： 读每个文件里的 `app_name` / `app_type` / `app_sub_type`，放进链表
- 输出： 全局链表 `g_map_entry`
- 给谁： 后面 `restore.c` 里 `map_found_queue`：引擎只给出类型编号时，用这张表翻成应用名写进日志。
  
  
  
  


4. 读配置、做本进程准备（145–147 行）

- `GlobalInit`：从 ini 读有几个网口、PCI 地址，填进 `m_DpdkInfo`
- `combine_rule_queue_init`：规则队列
- `map_protocol_load`：加载协议映射

6. 启动框架和 DPDK（150–151 行）

- `main_init`：框架初始化（在 `libframe` 里）
- `main_dpdk(...)`：真正开始收包。四个参数是回调：访问日志、监控日志、写 pcap、文件二次处理。收包、还原主要在这里面转，不在 `main` 的循环里。

7. 再开两条辅助逻辑（153–155 行）

- `PacketThread`：后台线程，写流量统计等
- `mon_init`：监控相关初始化
- 记下当前 snort 规则文件的 MD5
