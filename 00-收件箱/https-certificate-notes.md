# HTTPS 证书知识点

## 1. 证书是什么

HTTPS 里的证书通常指 SSL/TLS 证书。它是一份按标准格式生成的数字文件，可以理解为网站在网络通信中的“电子身份证”。

证书里通常包含：

- 网站域名或 IP 地址
- 网站公钥
- 证书有效期
- 证书颁发者
- 证书签名
- 证书用途

常见证书文件名包括：

```text
cert.pem
server.crt
fullchain.pem
```

如果打开 PEM 格式证书，通常会看到类似内容：

```text
-----BEGIN CERTIFICATE-----
MIIFazCCA1OgAwIBAgISA...
-----END CERTIFICATE-----
```

中间这一大段不是乱码，而是经过编码后的证书内容。

## 2. 证书的作用

证书主要有两个作用。

第一，证明网站身份。

浏览器用证书判断：我访问的 `example.com`，是不是真的 `example.com`，而不是被别人冒充的网站。

第二，帮助建立加密连接。

证书里有网站的公钥。浏览器可以用它参与 TLS 握手，和服务器协商出后续加密 HTTP 数据用的会话密钥。

注意：真正大量加密请求和响应的，一般不是证书本身，而是 TLS 握手后生成的会话密钥。

## 3. 证书是谁发的

公网 HTTPS 证书通常由 CA 证书机构签发，比如：

- Let's Encrypt
- DigiCert
- GlobalSign
- Sectigo
- 阿里云证书服务
- 腾讯云证书服务
- Cloudflare

CA 在签发前会验证：申请者是否真的控制这个域名。

如果是内网或本地测试环境，也可以自己签发证书，也就是自签名证书。但这种证书浏览器默认不信，除非把对应的根证书安装进客户端的受信任根证书列表。

## 4. 证书是给谁看的

证书主要是给客户端看的。

客户端可以是：

- 浏览器
- 手机 App
- 后端服务
- 命令行工具，比如 `curl`

当客户端访问 HTTPS 服务时，服务器会把证书发给客户端。客户端会检查：

- 域名或 IP 是否匹配
- 证书是否过期
- 证书链是否可信
- 证书是否被撤销

检查通过后，客户端才认为这个连接可信，然后继续建立加密通信。

## 5. HTTPS 连接流程

一次典型 HTTPS 连接的大致流程是：

```text
1. 服务器配置由浏览器信任链认可的证书和私钥
2. HTTPS 连接时，服务器在 TLS 握手中发送证书
3. 浏览器验证证书，确认服务器身份
4. 双方协商出会话密钥
5. 后续 HTTP 数据在 TLS 加密通道中传输
```

更具体地说：

1. 服务器上配置网站证书、证书链和对应私钥。
2. 浏览器访问 `https://...` 地址，开始 TLS 握手。
3. 服务器把证书发送给浏览器。
4. 浏览器验证证书是否可信、是否过期、是否匹配当前访问地址。
5. 浏览器和服务器协商出一个临时会话密钥。
6. 后续 HTTP 请求和响应都在 TLS 加密通道里传输。

证书用于证明服务器身份，并参与密钥协商；后续数据主要由会话密钥加密。

## 6. 内网 IP 访问为什么会出现证书问题

如果访问内网地址时出现：

```text
你的连接不是专用连接
攻击者可能试图从 172.16.130.231 窃取你的信息
net::ERR_CERT_COMMON_NAME_INVALID
```

核心原因通常是：浏览器访问的是一个 IP 地址，但服务器返回的证书并不声明自己属于这个 IP。

例如访问地址是：

```text
https://172.16.130.231:60001/login
```

但证书里写的是：

```text
DNS: internal.example.local
```

而不是：

```text
IP Address: 172.16.130.231
```

浏览器就会认为：这个证书不是发给 `172.16.130.231` 的，可能有人在冒充目标服务器。

这时 Chrome 会报：

```text
net::ERR_CERT_COMMON_NAME_INVALID
```

## 7. Common Name 和 SAN

早期证书里常用 `Common Name`，也就是 CN，表示证书对应的域名。

现代浏览器主要看 `Subject Alternative Name`，也就是 SAN。

所以即使 CN 写了某个域名或 IP，只要 SAN 里没有正确声明，也可能仍然报证书名称不匹配。

如果要用 IP 地址访问 HTTPS 服务，证书的 SAN 里应该包含：

```text
IP Address: 172.16.130.231
```

注意不要写成：

```text
DNS: 172.16.130.231
```

IP 地址应该作为 `IP Address` 类型写入 SAN。

## 8. 常见证书错误原因

常见证书问题包括：

- 证书过期
- 证书尚未生效
- 本机系统时间错误
- 访问地址和证书中的域名或 IP 不匹配
- 证书链不完整
- 证书由浏览器不信任的 CA 签发
- 内网自签名证书没有安装根证书
- 反向代理、网关、Nginx、负载均衡器配置了错误证书
- 公司代理、抓包工具或安全软件替换了 HTTPS 证书

不同错误码对应不同原因。

例如：

```text
net::ERR_CERT_COMMON_NAME_INVALID
```

通常表示访问地址和证书名称不匹配。

```text
net::ERR_CERT_AUTHORITY_INVALID
```

通常表示证书颁发机构不被浏览器信任。

## 9. 内网环境的常见解决方式

内网部署 HTTPS 服务时，常见解决方式有三种。

第一，使用证书匹配的内网域名访问。

例如证书签给：

```text
internal-web.company.local
```

就访问：

```text
https://internal-web.company.local:60001/login
```

同时通过 DNS 或 hosts 文件把这个域名解析到内网 IP。

第二，重新签发包含 IP 的证书。

如果必须使用 IP 访问，那么证书 SAN 中必须包含：

```text
IP Address: 172.16.130.231
```

第三，安装并信任内网 CA 根证书。

如果证书是公司 CA 或自签 CA 发的，需要把对应根证书安装到客户端系统或浏览器的受信任根证书列表中。

## 10. 一句话总结

HTTPS 证书的作用是证明服务器身份，并帮助浏览器和服务器建立安全加密通道。

内网 IP 访问报 `net::ERR_CERT_COMMON_NAME_INVALID`，通常不是 HTTPS 流程错了，而是服务器返回的证书和当前访问的 IP 地址对不上。
